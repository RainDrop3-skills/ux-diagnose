## 5. 인식의 용이성
사용자가 장애 유무와 관계없이 모든 콘텐츠를 동등하게 인식할 수 있어야 한다.

### 5.1.1 적절한 대체 텍스트 제공
**텍스트 아닌 콘텐츠는 그 의미나 용도를 인식할 수 있도록 대체 텍스트를 제공해야 한다.** 대체 텍스트는 간단명료하게 쓴다.
- 이미지 링크, 이미지 버튼: 핵심 기능을 간단한 대체 텍스트로 제공한다.
- 의미 있는 배경 이미지: 그 의미가 보조기술로 전달되도록 대체 텍스트를 제공한다.
- 데이터 차트처럼 복잡한 콘텐츠: 의미를 충분히 파악할 수 있는 대체 텍스트를 제공한다.
- 제공하지 않거나 제한적으로 제공해도 되는 경우
  - 대체 콘텐츠(예: 텍스트와 같은 내용의 수어 동영상)
  - 내용을 설명할 수 없는 경우(생방송, 색맹·청각·시력 검사, 받아쓰기 등): 간략한 용도만 알려도 된다.
  - 특정 감각으로만 제공되는 콘텐츠(플루트 독주, 시각 예술 작품): 간략한 용도만 알려도 된다.
  - 장식용 콘텐츠: 대체 텍스트로 **공백 문자**를 제공한다(설명하면 오히려 혼란).
  - 같은 정보의 중복: 보조기술로 같은 정보가 반복 전달되지 않게 하는 것이 바람직하다.

### 5.2.1 자막 제공
**멀티미디어 콘텐츠에는 자막, 대본 또는 수어를 제공해야 한다.** 멀티미디어와 동등한 내용이어야 한다.
- 가장 바람직한 방법은 오디오와 동기화된 폐쇄자막이다.
- 대사 없이 영상만 있으면 화면해설(텍스트, 오디오, 대본)을 제공한다. 음성만 있어도 자막, 대본 또는 수어를 제공한다.
- 자막, 대본, 수어 중 하나 이상을 제공하면 된다. 재생할 때마다 자막이 자동으로 표시되는 콘텐츠는 준수로 본다.

### 5.3.1 표의 구성
**표는 이해하기 쉽게 구성해야 한다.**
- 표 정보 제공: 표의 내용, 구조 등을 이해할 수 있는 정보를 제공해 이용 방법을 예측할 수 있게 한다.
- 표의 구성: 제목 셀과 데이터 셀이 구분되도록 구성한다.

### 5.3.2 콘텐츠의 선형구조
**콘텐츠는 논리적인 순서로 제공해야 한다.**
- 모든 콘텐츠는 내용을 이해할 수 있는 선형구조로 작성한다.
- 스타일 시트로 화면 배치를 바꾸더라도 콘텐츠의 나열 순서(선형구조)는 맥락을 이해할 수 있게 논리적으로 유지한다.

### 5.3.3 명확한 지시사항 제공
**지시사항은 모양, 크기, 위치, 방향, 색, 소리 등에 관계없이 인식될 수 있어야 한다.** 특정 요소를 가리키거나 지시사항을 전달하는 콘텐츠에만 적용한다.
- "동그란 버튼을 누르시오", "오른쪽 버튼을 누르시오"처럼 쓰면, 그 버튼의 대체 텍스트에 그 표현이 없을 때 시각장애인은 어느 요소인지 알 수 없다. 실제 명칭이나 대체 텍스트로 가리키거나 다른 감각의 정보를 함께 준다.
- 소리로만 알리지 않는다(예: 비프음으로 정답·오답을 알리면 시각적인 확인 수단도 준다).
- 텍스트 지시사항에는 별도 음성을 추가할 필요가 없다.

### 5.4.1 색에 무관한 콘텐츠 인식
**콘텐츠는 색에 관계없이 인식될 수 있어야 한다.** 색을 구별하지 못하는 사용자, 흑백 화면·인쇄, 고대비 모드 사용자도 인식할 수 있어야 한다.
- 색만으로 정보를 표현하지 않는다. 색은 시각적 강조로만 쓴다.
- 무늬 등으로도 구분하면 고대비·흑백 사용자도 구분할 수 있다.

### 5.4.2 자동 재생 금지
**자동으로 소리가 재생되지 않아야 한다.** 동영상, 오디오, 음성, 배경 음악 등 모든 소리가 대상이다.
- 3초 미만의 소리는 허용한다.
- 3초 이상 재생되는 소리는 멈춤, 일시정지, 음량 조절 등 제어 수단을 함께 제공한다.
- 자동 재생을 허용하는 경우: 3초 안에 멈추거나, 지정된 키(예: Esc)로 멈출 수 있게 한다.
- 권장: 멀티미디어는 정지 상태로 제공하고 사용자가 요구할 때만 재생한다.

### 5.4.3 텍스트 콘텐츠의 명도 대비
**텍스트 콘텐츠(텍스트, 텍스트 이미지)와 배경 간의 명도 대비는 4.5 대 1 이상이어야 한다.**
- 18pt 이상, 또는 14pt 이상 굵은 글꼴이면 3 대 1까지 낮출 수 있다. (보충: CSS로는 24px 이상, 또는 약 18.66px 이상이면서 굵기 700 이상)
- 화면 확대가 가능하도록 구현한 텍스트 콘텐츠는 3 대 1까지 낮출 수 있다.
- 예외: 로고, 장식 목적의 콘텐츠, 마우스나 키보드로 초점을 받았을 때 명도 대비가 커지는 콘텐츠.

### 5.4.4 콘텐츠 간의 구분
**이웃한 콘텐츠는 구별될 수 있어야 한다.** 시각적으로 구분되게 제공한다.
- 구분 방법 예: 테두리, 구분선, 서로 다른 무늬, 배경색 명도 대비(채도) 차이, 줄 간격·글자 간격 조절 등.

## 6. 운용의 용이성
사용자가 장애 유무와 관계없이 모든 기능을 운용할 수 있어야 한다.

### 6.1.1 키보드 사용 보장
**모든 기능은 키보드만으로도 사용할 수 있어야 한다.** 필요한 키 조작 횟수는 따지지 않는다.
- 예외: 커서 궤적이 중요한 콘텐츠(붓질, 시뮬레이션, 지리정보, 가상현실 등), 움직임 측정 센서를 쓰는 콘텐츠. 예외 콘텐츠라도 그 기능을 뺀 나머지 인터페이스는 키보드로 쓸 수 있어야 한다.

### 6.1.2 초점 이동과 표시
**키보드에 의한 초점은 논리적으로 이동해야 하며, 시각적으로 구별할 수 있어야 한다.**
- 초점 이동 순서는 사용자가 예측하는 순서(관례)와 일치해야 한다. 예: 아이디 → 비밀번호 → 로그인 버튼.
- 함정 방지: 키보드 조작이 불가능해지거나, 다음·이전 요소로 초점을 옮길 수 없는 상태가 되지 않아야 한다. 갑작스러운 페이지 전환도 일어나지 않아야 한다.
- 초점 시각화: 초점을 받은 콘트롤은 시각적으로 구별되어야 한다(예: 점선 테두리). 마우스 초점과 키보드 초점의 표시 방법이 달라도 된다. 초점 표시는 시간제한이 없어야 한다.

### 6.1.3 조작 가능
**사용자 입력 및 콘트롤은 조작 가능하도록 제공되어야 한다.** 이웃한 콘트롤을 개별적으로 선택해 쓸 수 있는 충분한 크기로 제공한다.
- 콘트롤 크기는 대각선 길이 6.0mm 이상이 바람직하다.
- 링크, 사용자 입력, 기타 콘트롤은 테두리 안쪽으로 1픽셀 이상 여백을 두고, 그 여백은 포인터 조작에 반응하지 않게 하는 것이 바람직하다.

### 6.1.4 문자 단축키 ★
**문자 단축키는 오동작으로 인한 오류를 방지하여야 한다.** 단일 문자 단축키(글자, 숫자, 구두점, 기호 키 하나)를 제공하면 다음 중 하나 이상을 충족한다.
- 비활성화: 단축키를 끌 수 있다.
- 재설정: 기능키(Ctrl, Alt, Shift, Option, Command 등)를 하나 이상 조합해 재설정할 수 있다.
- 초점을 받은 경우에만 활성화: 해당 구성요소(폼 콘트롤, 링크, 에디터 등)가 초점을 받았을 때만 동작한다.

### 6.2.1 응답시간 조절
**시간제한이 있는 콘텐츠는 응답시간을 조절할 수 있어야 한다.**
- 시간제한 콘텐츠는 가급적 넣지 않는다. 보안 등의 이유로 꼭 필요하면 회피 수단을 제공한다.
- 반응시간 조절 수단: 시간제한 해제 또는 연장. 조절 기능은 충분한 시간(최소 20초 이상) 전에 미리 알린다.
- 예외: 온라인 경매, 실시간 게임처럼 조절이 원천적으로 불가능한 경우(단, 시간제한이 있음을 미리 알리고 종료 시에도 알린다). 세션 시간이 20시간 이상인 경우.

### 6.2.2 정지 기능 제공
**자동으로 변경되는 콘텐츠는 움직임을 제어할 수 있어야 한다.**
- 스크롤되거나 자동 갱신되는 콘텐츠를 쓰지 않는 것이 우선이다.
- 쓰는 경우 일시 정지하고, 지나간 콘텐츠나 다음 콘텐츠를 선택할 수 있는 콘트롤(앞으로, 뒤로, 정지 등)을 제공한다. 예: 배너, 스크롤 뉴스.

### 6.3.1 깜빡임과 번쩍임 사용 제한
**초당 3~50회 주기로 깜빡이거나 번쩍이는 콘텐츠를 제공하지 않아야 한다.** 10인치 이상 화면에서 특히 주의한다.
- 번쩍임이 초당 3~50회이면, 10인치 이상 화면에서 번쩍이는 콘텐츠 면적의 합이 화면 전체의 10%를 넘지 않아야 한다.
- 초당 3~50회로 깜빡이는 콘텐츠는 깜빡임을 정지시킬 수 있어야 한다.
- 번쩍이는 시간을 3초 미만으로 제한하면 발작을 예방하면서도 중요성을 알릴 수 있다.

### 6.4.1 반복 영역 건너뛰기
**콘텐츠의 반복되는 영역은 건너뛸 수 있어야 한다.**
- 핵심 영역으로 바로 가는 건너뛰기 링크를 **웹 페이지의 가장 앞에** 제공한다.
- 건너뛰기 링크가 여러 개면 핵심 영역으로 가는 링크를 가장 먼저 둔다.
- 메뉴 건너뛰기 링크는 **화면에 보이도록** 구현해야 한다(지체장애인의 키보드 조작도 줄여 주기 때문).

### 6.4.2 제목 제공
**페이지, 프레임, 콘텐츠 블록에는 적절한 제목을 제공해야 한다.** 간단명료하게, 무엇인지 유추할 수 있게 쓴다.
- 웹 페이지 제목(title): 모든 페이지에 내용을 설명하는 제목을 주고, 페이지마다 유일하고 서로 달라야 한다.
- 팝업창에도 제목을 준다.
- 프레임 제목: 모든 프레임에 설명하는 제목을 준다. 내용 없는 프레임에도 "빈 프레임" 같은 제목을 준다.
- 콘텐츠 블록: 적절한 제목(heading)을 준다. 본문이 없는 블록에는 제목을 붙이지 않는다.
- 제목에 불필요한 특수 기호를 반복해 쓰지 않는다.

### 6.4.3 적절한 링크 텍스트
**링크 텍스트는 용도나 목적을 이해할 수 있도록 제공해야 한다.** 링크 텍스트만으로 또는 주변 맥락으로 충분히 이해할 수 있어야 한다.
- 문장 일부에 링크를 걸 때는 목적지·용도를 표현한 텍스트에 건다.
- "바로가기", "GO" 같은 링크는 목적지 정보를 주는 텍스트 바로 뒤에 둔다.
- 텍스트와 이미지 링크가 같은 곳으로 가면 하나의 링크로 묶는 것이 바람직하다. 이때 이미지 대체 텍스트는 공백으로 준다.
- 같은 제품을 다른 관점에서 설명한 페이지로 가는 링크들은 텍스트를 서로 다르게 하는 것이 바람직하다.
- 탭 콘트롤 옆 "더보기"는 맥락으로 "공지사항 더보기"임을 알 수 있어야 한다.
- 아이콘 링크(예: 집 모양 홈 링크)는 아이콘만으로 목적을 직관적으로 알 수 있어야 하고, 대체 텍스트는 5.1.1을 따른다.

### 6.4.4 고정된 참조 위치 정보 ★
**전자출판문서 형식의 웹 페이지는 각 페이지로 이동할 수 있는 기능이 있어야 하고, 서식이나 플랫폼에 상관없이 참조 위치 정보를 일관되게 제공·유지해야 한다.**
- 페이지 구분이 있는 전자출판문서는 페이지 번호 같은 참조 위치 정보와, 각 페이지로 이동하는 기능을 제공한다.
- 확대·축소나 플랫폼 변경에도 참조 위치 정보가 일관된 위치에 유지되어야 한다.

### 6.5.1 단일 포인터 입력 지원 ★
**다중 포인터 또는 경로기반 동작을 통한 입력은 단일 포인터 입력으로도 조작할 수 있어야 한다.**
- 다중 포인터: 핀치 줌, 두 손가락 탭 등. 경로기반 동작: 스와이프, 끌어서 놓기, 그리기 등.
- 예외: 필수적인 경우(피아노 앱 동시 누르기, 서명), 운영체제·브라우저·보조기기가 지원하는 동작(예: 두 손가락 스크롤).

### 6.5.2 포인터 입력 취소 ★
**단일 포인터 입력으로 실행되는 기능은 취소할 수 있어야 한다.** 다음 중 하나 이상을 지킨다.
- 다운 이벤트만으로 실행하지 않는다.
- 업 이벤트에 완료되며, 실행 전에 중지하거나 실행 후 취소할 수 있다.
- 다운 이벤트로 실행된 기능은 업 이벤트로 되돌릴 수 있다.
- 필수적인 경우(화면 피아노 건반, 슈팅 게임)는 예외.

### 6.5.3 레이블과 네임 ★
**텍스트 또는 텍스트 이미지가 포함된 레이블이 있는 사용자 인터페이스 구성요소는 시각적으로 표시되는 해당 텍스트를 네임에 포함해야 한다.**
- 네임과 보이는 텍스트는 같게 하는 것이 좋다. 다르게 할 경우 보이는 텍스트를 네임의 앞부분에 둔다.
- 텍스트가 포함된 레이블이 없는 구성요소에는 적용하지 않는다.

### 6.5.4 동작기반 작동 ★
**동작기반으로 작동하는 기능은 사용자 인터페이스 구성요소로 조작할 수 있고, 동작기반 기능을 비활성화할 수 있어야 한다.** 예: 흔들어서 실행 취소, 손동작으로 사진 촬영.
- 예외: 접근성 지원 인터페이스를 통한 조작(예: 안구마우스), 동작이 기능에 반드시 필요한 경우(예: 만보기).

## 7. 이해의 용이성
사용자가 장애 유무와 관계없이 콘텐츠를 이해할 수 있어야 한다.

### 7.1.1 기본 언어 표시
**주로 사용하는 언어를 명시해야 한다.** 웹 페이지의 기본 언어를 반드시 정의한다(화면낭독프로그램의 발음, 점역에 쓰인다).

### 7.2.1 사용자 요구에 따른 실행
**사용자가 의도하지 않은 기능(새 창, 초점에 의한 맥락 변화 등)은 실행되지 않아야 한다.** 기능은 마우스 클릭이나 키보드 조작으로 실행되어야 한다.
- 초점에 의한 맥락 변화 금지. 흔한 오류
  - 서식이 자동 제출됨
  - 새 창이 열림
  - 드롭다운이 열리기만 해도 메뉴 항목이 실행됨
  - 풀다운 메뉴에서 초점만 받아도 기능이 실행됨
  - 초점이 다른 콘트롤로 이동하거나 사라지거나 위치를 예측할 수 없음
- 입력에 따른 변화 금지: 콤보 박스, 라디오버튼, 체크박스에서 항목을 선택하는 것만으로 기능이 실행되거나 서식이 제출되면 안 된다. 함께 제공한 실행 버튼을 눌렀을 때 실행한다.
- 초점을 받은 요소의 색 반전·테두리 같은 시각적 변화, 초점이 이동하지 않은 상태에서 나타나는 추가 정보는 맥락 변화로 보지 않는다.
- 새 창·팝업창: 사용자가 예측할 수 없는 상황에서 열지 않는다.
- 레이어 팝업: 초점 이동과 선형구조를 해칠 가능성이 커서 쓰지 않는 것이 바람직하다.
- 새 창, 팝업창, 레이어 팝업은 닫기·종료 버튼을 누르면 실제로 닫혀야 한다.

### 7.2.2 찾기 쉬운 도움 정보 ★
**도움 정보가 제공되는 경우, 각 페이지에서 동일한 상대적인 순서로 접근할 수 있어야 한다.** 단일 페이지 앱이나 웹 페이지 묶음에서 아래 중 하나 이상을 제공하면, 최소 하나는 각 페이지에서 같은 상대적 순서로 제공한다.
- 담당자 상세 연락처(전화번호, 이메일, 운영시간), 담당자 연락 방법(메신저, 채팅, 게시판, SNS), 도움말(FAQ, 사용법), 자동화된 연결(챗봇).

### 7.3.1 오류 정정
**입력 오류를 정정할 수 있는 방법을 제공해야 한다.**
- 온라인 서식에서 오류가 나면 **오류가 발생한 위치와 오류 이유**를 알려 준다. 예: 필수 항목을 비우고 제출하면 어떤 항목이 누락됐는지 알린다.
- 오류 내용을 먼저 텍스트로 설명하거나, 오류 위치로 초점을 옮긴 뒤 설명하면 정정이 쉬워진다(기대효과).
- 시스템·플랫폼에서 발생한 오류에는 적용하지 않는다.

### 7.3.2 레이블 제공
**사용자 입력에는 대응하는 레이블을 제공해야 한다.** 레이블과 입력의 관계를 보조기술이 알 수 있게 대응시킨다. 근처에 텍스트만 두고 대응시키지 않으면 보조기술은 레이블을 인식하지 못한다.

### 7.3.3 접근 가능한 인증 ★
**인증 과정은 인지 기능 테스트에만 의존해서는 안 된다.** 인지 기능 테스트(비밀번호 입력, 패턴 인식, 임의 문자열 기억, 계산, 특정 객체가 든 이미지 찾기 등)에 의존하면, 의존하지 않는 인증 방법을 하나 이상 제공한다.
- 방법 예: 브라우저가 아이디·비밀번호를 저장할 수 있게 마크업한 서식, OAuth를 통한 서드파티 인증, 신체(얼굴, 지문)나 물건(휴대폰, USB) 인증.
- 사용자 이름, 이메일, 전화번호처럼 익숙한 정보는 인지 기능 테스트로 보지 않는다.

### 7.3.4 반복 입력 정보 ★
**반복되는 입력 정보는 자동 입력 또는 선택 입력할 수 있어야 한다.** 한 과정의 이전 단계에서 이미 입력했거나 제공된 정보를 다시 입력해야 하면 자동으로 채우거나 선택해 채울 수 있게 한다.
- 예: 주문자와 수령자 주소가 같으면 주문자 주소를 선택해 채운다.
- 예외: 비밀번호처럼 보안 목적으로 재입력이 필수인 경우.

## 8. 견고성
콘텐츠가 기술에 영향을 받지 않고 이용될 수 있어야 한다.

### 8.1.1 마크업 오류 방지
**마크업 언어의 요소는 열고 닫음, 중첩 관계 및 속성 선언에 오류가 없어야 한다.**
- 요소의 열고 닫음 일치(표준이 따로 정한 경우 제외), 요소의 중첩 오류 방지, 한 요소 안에서 속성 중복 선언 금지, 한 문서 안에서 id 값 중복 금지.

### 8.2.1 웹 애플리케이션 접근성 준수
**콘텐츠에 포함된 웹 애플리케이션은 접근성이 있어야 한다.** 플러그인이나 기능 실행에 필요한 웹 애플리케이션이 접근을 방해하지 않아야 한다.
- 운영체제·플랫폼이 제공하는 접근성 프로그래밍 인터페이스를 사용해 만든다.
- 그런 인터페이스가 없는 새 기능을 만들면, 기능의 **명칭, 역할, 상태, 값**을 접근성 인터페이스로 전달해 보조기술이 쓸 수 있게 한다. (보충: 웹에서는 시맨틱 HTML 요소와 WAI-ARIA의 role, aria-* 속성이 이 역할을 한다.)
- 국내 보조기술로 접근할 수 없는 웹 애플리케이션은 가능한 한 쓰지 않고, 꼭 써야 하면 대체수단을 제공한다.
